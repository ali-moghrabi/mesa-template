# MESA: setting up a new client

One repo serves every restaurant. Each client gets its own Vercel project and its own Render service from that repo, and the env var `MESA_SITE` decides which restaurant a deployment is.

## Layout (web, `client/`)

- `sites/<slug>/config.json`: the client's config. Commit it.
- `sites/<slug>/public/`: the client's logo and photos, served at `/site/…` (in config.json: `"site/hero.webp"`). Commit it.
- `config/config.json` and `public/site/`: generated by `scripts/use-site.mjs` before dev and build. Gitignored.
- `.private/`: env files with secrets. Gitignored, never commit.

## Shared vs per client

- **Shared:** one Vercel Pro team, one Atlas cluster, one S3 bucket, one email provider.
- **Per client:**
  - a Vercel project and a Render service
  - their own database `mesa_<slug>` (ideally with its own database user)
  - `S3_KEY_PREFIX=<slug>/`
  - their own secrets, Tap keys and domain

## Security settings (every client)

- **Secrets:** `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `COOKIE_SECRET` and `MFA_ENCRYPTION_KEY` must each be 32+ random characters, all different (the API refuses to start otherwise). Never reuse one client's secrets for another.
- **Visitor IP (rate limits and the sign-in lock depend on it):**
  - Render: `INTERNAL_PROXY_SECRET` = 32+ random characters. Vercel: `API_PROXY_SECRET` = the same value (server-only, never `NEXT_PUBLIC_`).
  - Render: `TRUST_PROXY` = the number of Render proxies. Find it once: set `SHOW_CLIENT_IP=true`, open `<api>/api/v1/auth/ip`, and raise `TRUST_PROXY` until `ip` is your real IP, even when calling with a fake `X-Forwarded-For` header. Then delete `SHOW_CLIENT_IP`.
  - `new-site` writes all of these itself: the proxy secret pair (same value on both sides) and `MFA_ENCRYPTION_KEY` are generated per client, and `TRUST_PROXY` is copied from `.private/shared.api.env` (it refuses to run while that's empty).
- `CLIENT_ORIGIN` must list the client's site exactly (`https://domain`, comma separated if several). It drives CORS and the CSRF check.
- Optional: `PASSWORD_BREACH_CHECK=off` turns off the breached-password check (on by default).

## Two-step sign-in (authenticator app)

- Free, no outside service: codes from Google Authenticator, Microsoft Authenticator, 2FAS, Aegis…
- Render: `MFA_ENCRYPTION_KEY` (required). **Never change it** once set: every saved authenticator would stop working and everyone would have to set it up again.
- `MFA_REQUIRED_ROLES`: who must use it.
  - Not set: staff, manager and admin (the admin panel).
  - `none`: nobody is forced. Use it for a public demo login (the API warns about it at startup).
  - Customers can always turn it on themselves from their account page.
- Optional `MFA_ISSUER`: the name shown in the app (defaults to `BRAND_NAME`).
- Team members set it up at their next sign-in (inside the sign-in window). Anyone already signed in is sent to the account page to set it up before the admin panel opens. Promoting someone signs them out, so they pass two-step sign-in in their new role.
- "Trust this device for 30 days" skips the code on that browser. Trusted devices, and sign-ins waiting for their code, are cancelled when 2FA is turned off or reset, the password is reset or changed, or the person signs out everywhere.
- **Lost phone:** sign in with a backup code (10, each works once).
  - No backup codes left: another admin uses "Reset two-step sign-in" on the Team page.
  - The only admin, or a customer: reset it in the database (`users`: set `mfaEnabled: false`, unset `mfaSecret`, `mfaRecoveryCodes`, `mfaLastStep`).

## Card payments (Tap, being replaced by Whish)

- Cards (Visa, Mastercard…) go through Tap Payments. Stripe has been removed. Whish will replace Tap once its API documentation arrives.
- Each restaurant opens its **own Tap account**. All its Tap settings go on its **Render** service (none on Vercel):
  - `TAP_SECRET_KEY` (`sk_test_…` / `sk_live_…`). Without it, card payments are off and only cash shows.
  - `TAP_PUBLIC_KEY` (`pk_test_…` / `pk_live_…`) and `TAP_MERCHANT_ID`. These show the **card field inside the checkout**. Without the public key, guests pay on Tap's own page instead.
- **Live card field:** Tap must register the restaurant's domain for its live public key. Ask Tap for each client.
- In `config.json`: `ordering.payments.methods` includes `"card"` (plus `"cod"` for cash).
- **Flow with the card field:**
  - The guest types the card in the checkout. Tap turns it into a one-time token, and card numbers never reach MESA.
  - The API charges the token.
  - If the bank asks for 3-D Secure, its check opens in a window over the checkout and ends on `/3ds-return`. That page is allowed in a frame in `next.config.ts`.
- **Flow without the card field:** Tap's page, then `/payment/complete`.
- Tap notifies the API at `<API_PUBLIC_URL>/api/v1/payments/tap/webhook`. On Render, the service's own address is used if `API_PUBLIC_URL` is empty. No webhook setup is needed in Tap's dashboard.
- Refunds are made from the admin panel and go through Tap.
- **Test cards:**
  - Visa `4508 7500 1574 1019` or Mastercard `5123 4500 0000 0008`, expiry `01/39`, CVV `100`.
  - Expiry `05/22` gives a decline.
  - Response 515 "Declined, Tap" means Tap's account setup. Ask Tap support.

## Steps

1. The onboarding email arrives with `<id>-config.json`.
2. `npm run new-site -- <file>`. Optional flags: `--slug`, `--domain`, `--api`.
3. Follow `.private/<slug>/CHECKLIST.md`:
   - add photos
   - preview with `MESA_SITE=<slug> npm run dev`
   - commit
   - create the Render service and paste `api.env`
   - create the Vercel project and paste `web.env`
   - set up the domain, and the Tap keys if they take cards
   - create the admin account (the owner sets up two-step sign-in at the first sign-in)
   - run test orders (cash and card) and bookings
4. `ONBOARDING_ENABLED=true` belongs only on **mesa-template.store**, on both its Vercel project (shows the form) and its Render API (accepts it). Never on a client's project: everywhere else the API rejects the form (404).

## Security audit

- Cloudflare's security-audit skill (in Claude Code) ran on mesa-template on 2026-10-29: no confirmed findings, 10 leads. All except the Tap webhook (Tap is being replaced by Whish) were fixed the same day.
- Re-run it before big releases: open Claude Code in the repo root and type `security audit this codebase`. Reports go to `~/security-audit-skill/mesa-template/run-<N>`; later runs build on earlier ones.
